## ③ 正文

### 3.1 两个探针的职责不能混

| 探针 | 回答的问题 | 失败后果 |
|---|---|---|
| liveness | 进程还活着吗 | 容器被**重启** |
| readiness | 能接流量吗 | 从负载均衡**摘除**，不重启 |

如果把数据库检查写进 liveness，PG 抖一下，K8s 会把所有 Pod 同时重启 ——
一次依赖故障被放大成全站雪崩。这是真实事故，不是理论。

readiness 失败必须返回 **503**。返回 500 会被当成代码 bug 触发告警，
503 的含义才是"我暂时不可用"。

### 3.2 async 与 `expire_on_commit`

SQLAlchemy 默认在 commit 后让所有对象属性失效（expire），
下次访问 `order.id` 时会**隐式发起 SELECT** 刷新。

同步模式下这是透明的小开销。但在 async 会话中，隐式 IO 会直接抛：

```text
MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here.
```

新人 90% 的时间消耗在这个报错上。解法是 `expire_on_commit=False`。

**代价**：commit 后对象里是"提交前的值"。如果别人并发改了这行，
你读到的是旧数据。所以交易场景里，commit 之后要展示给用户的数据，
应该重新查或在 commit 前就序列化成 DTO。这个坑 M3-04 会再遇到。

### 3.3 请求级 Session

`app/core/db.py` 里的 `get_db` 是全课程地基：

```python
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise
        else:
            if settings.tx_auto_commit:
                await session.commit()
```

关键点：**commit 写在 `yield` 之后的 `else` 分支**。
意思是"路由正常返回才提交，抛异常就回滚"。

现在先照抄，M0-02 会专门讲为什么不能在每个 service 里各自 commit。

### 3.4 连接池上限的算术

PG 的 `max_connections` 默认 100。可用连接数 = 实例数 ×（pool_size + max_overflow）。

```text
4 个 Pod × (10 + 20) = 120  >  100   → 第 4 个 Pod 启动后开始报 too many connections
```

所以 `pool_size` 不是"越大越好"，而是**总预算除以实例数**。
压测时先算这笔账，比调参有用。

### 3.5 Windows 环境的三个真坑

这三条是本次搭建时实际踩到的，每一个都能让人卡半小时以上。先记下来，省得你重踩。

**坑一：`localhost` 会解析到 `::1`**

```
REDIS_URL=redis://localhost:6379/0   # ❌ 连接挂起，不发错也不超时
REDIS_URL=redis://127.0.0.1:6379/0   # ✅
```

Windows 上 `localhost` 常优先解析为 IPv6 的 `::1`，而 Docker Desktop 的 IPv6 端口映射有时不通。
表现不是"连接被拒绝"，而是**一直挂着**，探针超时，接口无限等待。
`asyncpg` 会自动尝试多个地址所以侥幸能连，`redis-py` 不会。

配套的防御：任何客户端都必须显式设置 `socket_connect_timeout`。
没有超时的连接，在故障时会变成内存泄漏。

**坑二：`alembic.ini` 不能有中文**

Alembic 读取 `alembic.ini` 时用的是**系统 locale 编码**（中文 Windows 是 GBK），
而文件本身是 UTF-8。写一句中文注释就会炸：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0x8e
```

所以这个文件保持纯 ASCII，注释一律写英文。
源码文件（`.py`）没问题，只有 `.ini` 有这个限制。

**坑三：`httpx` 默认会走系统代理**

如果机器上配了全局代理（公司网络很常见），`httpx` 会读取注册表里的代理设置，
把 `http://127.0.0.1:8000` 也转发出去，于是拿到一个空的 **502**。

```python
httpx.AsyncClient(base_url=BASE_URL, trust_env=False)   # ✅
```

`curl` 和 `requests` 也有同样行为，排查时容易误判成"服务挂了"。
反过来看，这也是个好例子：**错误现象和真实原因常常隔着两层**。

## ⑤ 验收清单

逐条核对，任何一条不满足说明骨架有问题：

| # | 检查项 | 怎么验证 |
|---|---|---|
| 1 | `docker compose ps` 两个服务都是 `healthy` | 不是 `running`，是 `healthy` |
| 2 | `/health/live` 不触碰任何外部依赖 | 看代码，只有 return |
| 3 | `/health` 依赖故障时返回 503 而非 500 | 停掉 redis 再请求 |
| 4 | `expire_on_commit=False` | 读 `app/core/db.py` |
| 5 | 连接池有明确上限 | 读 `config.py` |
| 6 | 服务关闭时释放连接 | 看 `main.py` 的 lifespan |
| 7 | `.env` 在 `.gitignore` 里 | 密码不进仓库 |
| 8 | 连接串用 `127.0.0.1` 而非 `localhost` | 避免 IPv6 解析导致挂起 |
| 9 | Redis/HTTP 客户端都设了超时 | 依赖故障时快速失败 |
| 10 | `alembic.ini` 是纯 ASCII | GBK locale 下不会解码失败 |

### AI 在这个环节的典型错误

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 忘记 `expire_on_commit=False` | 随机 `MissingGreenlet` | 全局设 False |
| URL 用 `postgresql://` 配 async engine | 启动报 driver 不匹配 | 必须 `postgresql+asyncpg://` |
| health 里查业务表 | 空库启动即 unhealthy | 只做 `select 1` |
| 每个接口自己 `create_engine` | 连接泄漏、池失效 | 全局单例 + 依赖注入 |
| 把 `print` 当日志 | 线上无法检索 | 结构化日志（M6-01） |

## ⑥ 破坏性验证

```powershell
docker compose stop redis
python scripts/smoke.py health     # 期望 503，且 db=ok redis=down
docker compose start redis
python scripts/smoke.py health     # 期望恢复 200
```

再做一次存活验证：

```powershell
docker compose stop db
python scripts/smoke.py health
# 结果应是 503，但 uvicorn 进程不能崩 —— 这证明探针没有拖垮应用
```
