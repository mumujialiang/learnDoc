# 课程大纲：商城 + ERP 后端工程

## 定位

面向有 5 年前端经验、正在转全栈的工程师。前提假设：

- 语法、框架 API、CRUD 不构成障碍，不必细讲
- AI 承担绝大部分代码产出，人的价值在**判断**
- 每节课的产出不是"能跑的代码"，而是**能识别 AI 写错的代码**

因此每节课的固定结构：

```text
① 业务场景    一段真实且模糊的需求
② 你先想      10 分钟，写下数据模型和接口，不许问 AI
③ AI 实现     先出方案，再出代码
④ 验收清单    对照清单挑错，清单标注"AI 大概率错在哪"
⑤ 破坏性验证  并发 / 脏数据 / 重复请求 / 依赖故障
⑥ ADR         3 句话：为什么这么选，代价是什么
```

②和④是全部价值所在，跳过则无效。

## 主线项目

商城与 ERP 共享一套主数据。这不是为了省事，而是本课程的核心命题：

> "商城显示库存 10 件"和"仓库里实际有 10 件"不是同一个数字。

两者之间隔着预占、在途、锁定、批次、成本。把这条链路亲手走通一次，
对电商/ERP 后端的理解会超过写三年 CRUD 的人。

```text
        ┌──────────────┐         ┌──────────────┐
        │  MiniMall    │         │  MiniERP     │
        │  用户下单支付 │         │ 采购入库调拨 │
        └──────┬───────┘         └──────┬───────┘
               │                        │
        ┌──────┴────────────────────────┴──────┐
        │  共享主数据                            │
        │  商品 SPU/SKU · 库存台账+余额 · 单据    │
        └───────────────────────────────────────┘
```

## 模块总览

| 编号 | 课程 | 核心不变量 |

| M0-02 | 事务边界 | 一个请求一个事务，事务内禁止外部 IO |
| M0-03 | 幂等 | 任何写接口都可能被执行 2 次以上 |
| M0-04 | 错误处理与统一响应 | 错误码是契约，不是日志 |

| M1-04 | 状态机 | 状态只能沿合法边迁移 |
| M1-05 | 软删除、审计字段、乐观锁 | 数据要能回答"谁在何时改了什么" |

| M2-05 | 接口版本与兼容 | 前端不升级你也不能炸 |
| **M3 交易核心** ⭐ | | |

| M3-02 | 价格计算与优惠分摊 | 分摊误差必须能被吸收 |

| M3-04 | 下单扣减 | 超卖只发生在并发窗口 |
| M3-05 | 支付回调 | 回调一定重复、一定乱序 |

| M4-01 | 单据模型 | 库存只能被单据改变 |
| M4-02 | 库存台账 vs 余额 | 台账是事实，余额是缓存 |

## 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| Web | FastAPI | Pydantic 模型对前端像 TS interface，心智迁移顺 |
| ORM | SQLAlchemy 2.0 async | 显式查询，适配合复杂业务 SQL（ERP 需要） |
| 驱动 | asyncpg | 交易接口大量 IO 等待 |
| 数据库 | PostgreSQL 16 | 窗口函数、JSONB、部分索引、`ON CONFLICT` |
| 缓存 | Redis 7 | 库存预占、热点缓存 |
| 迁移 | Alembic | 可回滚的 schema 演进 |
| 队列 | ARQ（M5 引入） | 比 Celery 轻，原生 async |

不用 Django 的原因：商城/ERP 有大量非常规查询和显式锁需求，
Django ORM 在这些场景需要频繁绕行。但它的 Admin 的确适合做 ERP 后台，
M4-06 会作为对照提及。
