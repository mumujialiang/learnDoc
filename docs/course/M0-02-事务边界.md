# M0-02 事务边界

> 模块：M0 后端心智模型 ｜ 预计 60 分钟 ｜ 前置：M0-01

## ① 业务场景

> "用户下单后调用短信服务失败，订单却没创建成功，还提示了 500。"

这是初级后端最经典的 bug，也是前端转后端的第一道真正的墙。
前端的心智里只有"成功/失败"，后端的心智里必须还有**"部分成功"**。

## ② 你先想 10 分钟

1. 一个请求进来，事务应该在**哪一行**开始、哪一行结束？
2. 如果请求里既要写库又要调第三方 HTTP，先后顺序应该是？
3. 一个 service 方法被两个不同的路由复用，它自己 commit 会怎样？

## ③ 正文

### 3.1 事务边界 = 请求边界

本项目的约定：**一个 HTTP 请求 = 一个数据库事务**。

边界由 `get_db` 依赖统一持有：

```python
async with SessionLocal() as session:
    try:
        yield session          # 路由在这里执行
    except Exception:
        await session.rollback()
        raise
    else:
        await session.commit()  # 只有正常返回才提交
```

路由和 service 里**只 `flush`，不 `commit`**：

```python
@router.post("/orders")
async def create_order(body: OrderCreate, session: AsyncSession = Depends(get_db)):
    order = Order(...)
    session.add(order)
    await session.flush()   # 拿到 order.id，但事务未提交
    return order            # 依赖层负责 commit
```

`flush` 的作用：把 SQL 发出去、拿到自增 ID、**但不结束事务**。
`commit` 的作用：结束事务、释放锁、让其他事务看见。

### 3.2 为什么不能让 service 自己 commit

反例：

```python
async def create_order(session, body):
    order = Order(...)
    session.add(order)
    await session.commit()          # ❌ 事务 1

async def deduct_stock(session, sku_id, qty):
    await session.execute(update(...))
    await session.commit()          # ❌ 事务 2
```

一个下单请求变成两个独立事务。如果 `deduct_stock` 失败：

- 事务 1 已提交 → 订单存在
- 事务 2 回滚 → 库存没扣

结果：**卖出了没有库存的订单**。而且你没有任何机制能自动发现它。

这就是"部分提交"。它是所有数据不一致问题的源头。

### 3.3 事务内禁止外部 IO

这是本课最重要的一条铁律：

```python
async with session.begin():
    order = Order(...)
    session.add(order)
    await sms.send(...)     # ❌ 灾难
```

为什么是灾难，三个理由：

1. **外部服务无法回滚**。短信发出去了，你回滚数据库，用户收到"下单成功"但订单不存在。
2. **长事务**。短信接口超时 30 秒，你的数据库锁就被握 30 秒，其他请求全部排队。
3. **连接占用**。事务未结束，连接不能归还池子。发 50 条短信 = 50 个连接被占住。

正确顺序：

```text
1. 事务内：写订单 → commit
2. 事务外：发 MQ / 调短信 / 通知
3. 失败：走重试或补偿，不回滚订单
```

订单已经成立，通知失败只是通知失败。**业务事实的优先级永远高于副作用**。

### 3.4 长事务的两种形态

| 形态 | 表现 | 成因 |
|---|---|---|
| 显式长事务 | `idle in transaction` 长时间不降 | 事务里做了慢操作 |
| 隐式长事务 | 同一连接反复出现短事务 | 忘了提交，或 autocommit 关闭 |

第一种可以在 `pg_stat_activity` 里直接看到。第二种要靠监控提交频率。

`idle in transaction` 是 PG 里最危险的连接状态：
它持有快照，会**阻止 vacuum 回收死元组**。跑久了表会膨胀。

## ④ 动手实验：看见长事务

**终端 A**（提前开，持续观察）：

```powershell
python scripts/smoke.py inspect -r 10
```

**终端 B**（并发打事务内慢接口）：

```powershell
python scripts/smoke.py hammer -c 50 -s 10
```

观察终端 A 的输出。你应该看到 `idle in transaction` 从 1 涨到 **30 左右**然后回落。

为什么是 30 而不是 50？因为 `pool_size=10 + max_overflow=20 = 30`。
第 31 个请求拿不到连接，只能在池子外排队 —— 这就是连接池上限的直观体现。

也可以直接查：

```powershell
docker compose exec db psql -U mall -c "select state, count(*) from pg_stat_activity where datname='mall' group by 1;"
```

## ⑤ 验收清单

| # | 检查项 | 怎么验证 |
|---|---|---|
| 1 | 路由里没有 `session.commit()` | `grep -r "session.commit" app/` |
| 2 | 一个请求只产生一个事务 | 开 PG 日志，看 `BEGIN`/`COMMIT` 次数 |
| 3 | 事务内没有 `httpx` / `requests` 调用 | 读代码 |
| 4 | 异常路径会回滚 | 故意抛异常，检查数据没写进去 |
| 5 | service 层可被复用 | 不依赖自己的 commit |
| 6 | Session 不跨请求传递 | 没有把 session 塞进全局或后台任务 |

### AI 的典型错误

| 坑 | 后果 |
|---|---|
| 在每个 service 方法里 `commit()` | 部分提交，数据不一致 |
| `try/except` 吞异常后 `return {"code": 0}` | 依赖层认为成功，照样 commit |
| 事务里 `await httpx.post(...)` | 长事务 + 不可回滚 |
| commit 后继续读对象属性 | `expire_on_commit` 一开就炸 |
| 把 `AsyncSession` 传进 `BackgroundTasks` | 请求结束 session 已关闭 |
| 用 `session.begin()` 嵌套 `get_db` 的事务 | `InvalidRequestError: already begun` |

## ⑥ 破坏性验证

### 实验一：异常是否真回滚

临时加一个接口，写库后抛异常：

```python
@router.post("/playground/rollback-test")
async def rollback_test(session: AsyncSession = Depends(get_db)):
    await session.execute(text("insert into _probe(value) values ('should_rollback')"))
    raise RuntimeError("boom")
```

先建表 `create table _probe(id bigserial, value text);`，调用接口后再查：

```sql
select count(*) from _probe;   -- 必须是 0
```

如果不是 0，说明你的异常被某处吞掉了。

### 实验二：外部依赖失败是否拖垮事务

用 `httpbin` 的 delay 端点模拟第三方超时：

```python
await client.get("https://httpbin.org/delay/10")
```

放进事务里跑，再并发打 30 次，你会看到连接池被吃光、其他接口全部超时。
这就是"短信服务挂了导致整个商城下不了单"的真实成因。

## ⑦ ADR

```markdown
# 002 事务边界由依赖层统一持有

## 决策
一个 HTTP 请求一个事务，commit 由 get_db 依赖在正常返回时执行，
路由与 service 只 flush。

## 代价
- service 不能被单独当作"独立事务单元"复用
- 批量任务需要在任务层自己管理事务
- 需要团队纪律：任何人写 commit() 都要被 review 拦住

## 收益
- 不会出现部分提交
- 事务范围可审计（就在一个函数里）
- 路由代码不需要考虑事务
```
